# v1.0.0 — Locked Decisions

Eight decisions that shape the ISO 3166 registry. Each records the
choice, the alternatives considered, and the reason. Modifications
require a new ADR; the numbering D1–D8 is stable and referenced from
`CONTRIBUTING.md`.

Status: **locked** as of 2026-09-22.
Supersedes: none.
Superseded by: none.

---

## D1 — New repository, not a monorepo

**Decision.** `github.com/slimissa/iso3166` is a standalone
repository. It does not share code, CI, or versioning with
`slimissa/iso4217` or `slimissa/exchange-calendar`.

**Alternatives considered.**

- Monorepo with all registries under one roof.
- Subdirectory of `iso4217`.

**Reason.** A country is not a currency. Coordinated releases of
unrelated artifacts are a tax with no payoff. ISO 3166 versions
independently from v1.0.0. Cross-registry validation is solvable via
committed snapshots (see D5), not by co-locating code.

---

## D2 — Coverage

**Decision.** The registry contains four layers, distinguished by a
per-entry `status` field:

| Layer | Approx. count | `status` value |
|-------|---------------|----------------|
| Officially-assigned ISO 3166-1 codes | 249 | `officially-assigned` |
| Exceptionally-reserved codes (`UK`, `EU`, …) | ~13 | `exceptionally-reserved` |
| User-assigned codes (`XK`, `XX`, `ZZ`, …) | ~4 | `user-assigned` |
| Withdrawn ISO 3166-3 codes | ~30 | `withdrawn` |

**Alternatives considered.**

- Officially-assigned only (249 entries).
- Officially-assigned + user-assigned.
- Officially-assigned + user-assigned + exceptionally-reserved + withdrawn (chosen).

**Reason.** User-assigned and exceptionally-reserved codes appear in
real systems (Kosovo as `XK`, the UK as `UK` in trade documents).
Excluding them forces every consumer to maintain a supplement, which
is exactly the problem this registry exists to solve. Including them
with a `status` field is the same pattern ISO 4217 uses for
active/withdrawn/non-ISO.

Historical names before 1974 are out of scope — the standard does not
track them. See D8.

## D3 — Data model

**Decision.** Twelve fields per active entry, plus three for withdrawn.

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `alpha_2` | string | yes | Primary key. `^[A-Z]{2}$`. |
| `alpha_3` | string | yes | `^[A-Z]{3}$`. |
| `numeric` | string | yes | `^[0-9]{3}$`. Zero-padded string, not integer. |
| `name` | string | yes | ISO 3166 English short name. |
| `status` | string | yes | One of the four values in D2. |
| `independent` | boolean | yes | ISO's sovereignty flag. |
| `official_name` | string | no | ISO's full official name. |
| `region` | string | no | UN M49 macro-region. |
| `subregion` | string | no | UN M49 sub-region. |
| `intermediate_region` | string | no | UN M49 intermediate region. |
| `currency_codes` | list[string] | no | ISO 4217 alpha-3 codes. |
| `calling_codes` | list[string] | no | ITU-T E.164 prefixes. |
| `tlds` | list[string] | no | IANA ccTLDs. |
| `languages` | list[string] | no | ISO 639-3 codes. |
| `borders` | list[string] | no | Adjacent `alpha_2` codes. |
| `note` | string | no | Anything the standard does not capture. |
| `last_verified` | string | no | ISO date of last manual check. |
| `withdrawal_date` | string | withdrawn only | ISO 3166-3 date. |
| `replaced_by` | list[string] | withdrawn only | Successor `alpha_2` codes. |

**Alternatives considered.**

- `numeric` as integer. Rejected — `numeric` is a SQL reserved word,
  and leading zeros are meaningful for codes `< 100`.
- `alpha2` (no underscore). Rejected — inconsistent with the visual
  form `alpha-2` and with `currency_codes`.
- `currencies` instead of `currency_codes`. Rejected — "currencies"
  reads as full objects; `_codes` is unambiguous.

**Reason.** Mirrors ISO 4217's field naming and type choices wherever
the two standards have equivalent concepts. `currency_codes` is the
one field that exists specifically to make the cross-registry join in
D5 possible.

## D4 — Array split: `active` / `withdrawn`

**Decision.** The top-level `countries` object has two arrays:
`active` and `withdrawn`. `active` contains all entries with `status`
in `{officially-assigned, user-assigned, exceptionally-reserved}`.
`withdrawn` contains entries with `status == "withdrawn"`.

**Alternatives considered.**

- One flat `countries` array; consumers filter on `status`.
- Three arrays: `active`, `reserved`, `withdrawn`.

**Reason.** Matches ISO 4217's `active`/`withdrawn` split, which
consumers and wrappers already understand. Two arrays, not three,
because user-assigned and exceptionally-reserved are rare enough that
splitting them out is not worth the API surface.

---

## D5 — Cross-registry validation via committed snapshots

**Decision.** `tools/iso4217_snapshot.json` holds the set of ISO 4217
alpha codes the registry validates against. Validation checks that
every `currency_codes` entry exists in the snapshot. The snapshot is
updated by hand when ISO 4217 ships a new version, and `CHANGELOG.md`
records the refresh.

Symmetrically, the ISO 4217 repository will hold
`tools/iso3166_snapshot.json` and a mirror check job.

**Alternatives considered.**

- Live `pip install` of the sibling registry at validate time.
- Git submodule.
- Monorepo.

**Reason.** No runtime cross-repo dependency, no version pinning, no
coordination. A snapshot is a JSON file and a one-line pull request.
It is how OpenAPI specs reference each other.

The snapshot check is **advisory (warn, not fail)** in v1.0.0 and
becomes **blocking** in v1.0.1, once both repos have shipped once and
the refresh cadence is understood.

---

## D6 — Tooling: copy and adapt, no shared library

**Decision.** `tools/export_sql.py`, `tools/export_csv.py`,
`tools/export_parquet.py`, and `tools/validate.py` are ported from
ISO 4217 and adapted to the country schema. They are not extracted
into a shared `iso_registry_toolkit`.

**Alternatives considered.**

- Shared library as a third repository.
- Git submodule.

**Reason.** A shared library creates a third repository with its own
release cycle before either registry has proven it needs one. The
generators are roughly 350 lines each and the tests prove they work.
If a third registry (ISO 639, ISO 8601, ISO 20022) is added, revisit
then.

## D7 — Versioning: single source, all references agree

**Decision.** `VERSION` is the single source of truth. The following
must all match at every commit:

- `VERSION`
- `CHANGELOG.md` top `[x.y.z]` heading
- `README.md` version badge
- `iso3166.json` → `meta.version`
- Parquet footer `iso3166.version`

CI fails if any of the five disagree. Wrapper package versions
(`setup.py`, `package.json`, `Cargo.toml`, `go.mod`) are independent
and documented per wrapper.

**Alternatives considered.**

- Version only in `iso3166.json`, derived elsewhere.
- Version in two places (data and wrapper).

**Reason.** This is the single failure mode that cost ISO 4217 the
most rework. Centralize the check before the first release, not after.

---

## D8 — Out of scope for v1.0.0

| Excluded | Reason |
|----------|--------|
| ISO 3166-2 subdivisions | ~5,000 entries; separate registry. |
| Pre-1974 historical names | The standard does not track them. |
| Country names in other languages | Belongs in a locale layer, not the code list. |
| GDP, population, area | Not code-list data. |
| Disputed-territory judgments | The registry reports the standard; the standard is the authority. |
| Full ISO 3166-3 historical record | The ~30 currently-tracked withdrawn codes are in scope; deeper history is deferred. |
